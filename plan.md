# План pet-проекта: многопоточный key-value сервер

Цель: ~300-500 строк, которые ты понимаешь целиком. Проект собирает вместе всё из недель 1-2: RAII, const correctness, move-семантику, потоки, mutex, пул потоков, STL-контейнеры, сокеты и фрейминг TCP.

## Как пользоваться этим планом

- Иди **строго по шагам**. Каждый шаг маленький и проверяется отдельно, не переходи дальше, пока текущий не прошёл проверку.
- В каждом шаге: цель → что написать (скелет с `TODO`) → как проверить → типичные ошибки → вопросы на понимание.
- Скелеты задают только **форму**, тела функций пишешь сам. Если в твоём коде есть строка, смысл которой непонятен, — это сигнал разобраться, а не идти дальше.
- Застрял — смотри раздел "Если застрял" в конце.

## Что получится

```
$ nc localhost 8080
SET city Amsterdam
OK
GET city
Amsterdam
GET country
NOT_FOUND
DEL city
OK
FOO
ERR unknown command
```

## Протокол (фиксируем сразу)

| Запрос | Ответ |
|---|---|
| `SET <key> <value>` | `OK` (value — всё после ключа до конца строки, может содержать пробелы) |
| `GET <key>` | значение или `NOT_FOUND` |
| `DEL <key>` | `OK` или `NOT_FOUND` (ключа не было) |
| неизвестная команда | `ERR unknown command` |
| неверное число аргументов | `ERR wrong number of arguments` |

Правила:
- Одна команда — одна строка, оканчивается `\n` (`\r\n` тоже принимаем: `\r` в конце срезаем).
- Ответ — одна строка, оканчивается `\n`.
- Ключ — слово без пробелов.
- Максимальная длина строки — 64 КБ; длиннее — закрываем соединение (защита от клиента, который шлёт бесконечную строку).

## Что НЕ входит в проект (чтобы не распухло)

Сохранение на диск, TTL, авторизация, `epoll`/неблокирующие сокеты, HTTP, Boost.Asio. Всё это можно добавить потом, но не сейчас.

## Подготовка

- Нужна POSIX-система (Linux/macOS; на Windows — WSL).
- Возможная структура (на старте можно всё в одном `main.cpp` и разнести потом):

```
kv/
  main.cpp
  socket_handle.h    шаг 1
  net_utils.h        шаги 2-3: create_listener, LineReader, send_all
  kv_store.h         шаг 4
  command.h          шаг 4: handle_command
  thread_pool.h      шаг 5 (из конспекта по многопоточности)
```

- Сборка: `g++ -std=c++17 -Wall -Wextra -g -pthread main.cpp -o kv`
- Санитайзеры — **отдельные** сборки (ASan и TSan вместе не работают):
  - `-fsanitize=address,undefined` — утечки, выход за границы, UB
  - `-fsanitize=thread` — гонки данных
- Клиент для проверки: `nc localhost 8080`. Если `nc` не завершается после конца ввода — Ctrl+C (в некоторых версиях помогают флаги `-q 1` или `-N`).
- Нужные заголовки: `<sys/socket.h> <netinet/in.h> <unistd.h> <csignal> <cerrno> <cstring> <stdexcept> <string> <unordered_map> <mutex> <optional> <thread>`

## Шаг 1. RAII-обёртка над дескриптором

**Цель:** чтобы fd закрывался сам при любом выходе из области видимости.

**Скелет:**

```cpp
class SocketHandle {
    int fd_ = -1;
public:
    SocketHandle() = default;
    explicit SocketHandle(int fd);                       // забирает владение fd
    ~SocketHandle();                                     // close(fd_), если fd_ != -1
    SocketHandle(const SocketHandle&) = delete;
    SocketHandle& operator=(const SocketHandle&) = delete;
    SocketHandle(SocketHandle&& other) noexcept;         // TODO: забрать fd, у other поставить -1
    SocketHandle& operator=(SocketHandle&& other) noexcept;  // TODO: закрыть свой fd, затем забрать чужой
    int get() const;                                     // сырой fd для recv/send
    bool valid() const;
};
```

**Как проверить:** напиши маленький тест: создай сокет через `::socket(AF_INET, SOCK_STREAM, 0)`, оберни в `SocketHandle`, перемести в другой `SocketHandle`, дай обоим выйти из области видимости. Убедись, что `close` вызвался ровно один раз (временный `std::cerr` в деструкторе подойдёт).

**Типичные ошибки:**
- В move-присваивании забыли закрыть уже владеемый fd (утечка).
- В move-конструкторе забыли обнулить fd у источника (двойной `close`).
- Нет проверки `this != &other` в move-присваивании.

**Вопросы на понимание:**
- Почему копирование запрещено, а перемещение разрешено?
- Зачем `noexcept` у перемещающих операций?
- Что случится при двойном `close` одного и того же fd (и почему это опаснее, чем кажется, когда потоки открывают новые fd параллельно)?

## Шаг 2. Однопоточный эхо-сервер

**Цель:** увидеть весь путь `socket → bind → listen → accept → recv/send → close` в своём коде.

**Скелет** (одна функция разобрана целиком как образец, остальное — сам):

```cpp
SocketHandle create_listener(uint16_t port) {
    int fd = ::socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0)
        throw std::runtime_error(std::string("socket: ") + std::strerror(errno));
    SocketHandle sock(fd);          // с этого момента fd под защитой RAII:
                                    // если дальше что-то бросит исключение, fd закроется сам
    // TODO: setsockopt(SO_REUSEADDR)
    // TODO: заполнить sockaddr_in (не забыть htons), bind, проверка ошибки
    // TODO: listen, проверка ошибки
    return sock;
}

void serve_echo(SocketHandle client);       // TODO: recv -> send, пока recv > 0

int main() {
    auto listener = create_listener(8080);
    while (true) {
        int fd = ::accept(listener.get(), nullptr, nullptr);
        if (fd < 0) continue;       // TODO: подумай, когда это ошибка, а когда EINTR
        serve_echo(SocketHandle(fd));
    }
}
```

**Как проверить:**
1. `./kv`, в другом терминале `nc localhost 8080`, печатай строки — должны возвращаться.
2. Не закрывая первый `nc`, открой второй и напиши что-нибудь — **ответа не будет**. Закрой первый (Ctrl+C) — второй "оживёт".

**Типичные ошибки:**
- Забыли `SO_REUSEADDR` → после перезапуска `Address already in use`.
- Забыли `htons` → сервер слушает не тот порт.
- Не проверяют `-1` у `bind`/`listen` → сервер "запустился", но ничего не слушает.

**Вопросы на понимание:**
- Почему второй `nc` "завис"? В какой строке кода сервер сейчас стоит?
- Сколько дескрипторов у процесса, пока подключён один клиент? (Подсказка: слушающий + клиентский + stdin/stdout/stderr.)
- Что вернёт `recv`, когда клиент нажмёт Ctrl+C в `nc`?

## Шаг 3. Чтение строк с буферизацией

**Цель:** научиться работать с TCP как с потоком байтов — вырезать из него строки по `\n`, как бы ни порезала данные сеть.

**Скелет:**

```cpp
class LineReader {
    int fd_;
    std::string buf_;                          // накопленные, но ещё не разобранные байты
public:
    explicit LineReader(int fd);
    // true — в line лежит очередная строка (без '\n' и без '\r' в конце)
    // false — соединение закрыто, ошибка или строка слишком длинная
    bool read_line(std::string& line);
};

bool send_all(int fd, const std::string& data);   // цикл по send до конца (см. конспект по сетям)
```

**Идея `read_line`** (алгоритм, не код):
1. Ищи `'\n'` в `buf_`. Нашёл — вырежи строку, удали её (вместе с `\n`) из `buf_`, срежь `\r` в конце, верни `true`.
2. Не нашёл — сделай `recv` в локальный буфер (например, 4096 байт). `n <= 0` → верни `false`. Иначе допиши прочитанное в `buf_` и вернись к пункту 1.
3. Если `buf_` вырос больше 64 КБ без `\n` — верни `false` (клиент ведёт себя неадекватно).

Не забудь: `signal(SIGPIPE, SIG_IGN);` в начале `main`, иначе запись в закрытый клиентом сокет убьёт сервер.

**Как проверить** (подключи `LineReader` и `send_all` к эхо-серверу; он должен возвращать каждую строку отдельно):
- Обычный случай: набирай строки руками в `nc`.
- Две строки одним куском: `printf 'A\nB\n' | nc localhost 8080` → должно вернуться `A` и `B`.
- Строка по частям: `(printf 'hel'; sleep 1; printf 'lo\n') | nc localhost 8080` → ответ `hello` один раз, после паузы.
- Длинная строка: `head -c 100000 /dev/zero | tr '\0' 'a' | nc localhost 8080` → сервер закрывает соединение, но не падает.

**Типичные ошибки:**
- Считают, что один `recv` = одна строка (ломается на тестах "две строки" и "по частям").
- Теряют данные, оставшиеся в `buf_` после вырезания строки.
- Не срезают `\r` — `nc` на некоторых системах шлёт `\r\n`.

**Вопросы на понимание:**
- Почему `LineReader` хранит `buf_` между вызовами `read_line`, а не создаёт его заново?
- Что произойдёт без ограничения длины строки, если клиент будет слать байты без `\n`?
- Почему `send` тоже нужен в цикле?

## Шаг 4. KVStore и разбор команд

**Цель:** потокобезопасное хранилище и функция, превращающая строку-команду в строку-ответ. Сеть тут не нужна — это тестируется отдельно.

**Скелет:**

```cpp
class KVStore {
    std::unordered_map<std::string, std::string> data_;
    mutable std::mutex m_;                          // mutable — зачем? (см. вопрос ниже)
public:
    void set(const std::string& key, std::string value);
    std::optional<std::string> get(const std::string& key) const;
    bool del(const std::string& key);               // true, если ключ существовал
    size_t size() const;
};

// Принимает строку команды (без '\n'), возвращает ответ (без '\n').
std::string handle_command(KVStore& store, const std::string& line);
```

**Подсказка по разбору:** `std::istringstream iss(line); iss >> cmd >> key;`, а значение для `SET` — это остаток строки: `std::getline(iss, value)` и срезать ведущий пробел.

**Как проверить без сети:**

```cpp
KVStore store;
assert(handle_command(store, "SET a 1") == "OK");
assert(handle_command(store, "GET a") == "1");
assert(handle_command(store, "GET b") == "NOT_FOUND");
assert(handle_command(store, "DEL a") == "OK");
assert(handle_command(store, "DEL a") == "NOT_FOUND");
assert(handle_command(store, "FOO") == "ERR unknown command");
assert(handle_command(store, "SET onlykey") == "ERR wrong number of arguments");
```

Многопоточный тест:

```cpp
KVStore store;
std::vector<std::thread> threads;
for (int t = 0; t < 4; ++t)
    threads.emplace_back([&store, t] {
        for (int i = 0; i < 10000; ++i)
            store.set("k" + std::to_string(t) + "_" + std::to_string(i), "v");
    });
for (auto& th : threads) th.join();
assert(store.size() == 40000);
```

Прогони его в сборке с `-fsanitize=thread`. Потом **специально убери `lock_guard`** из `set` и прогони ещё раз — TSan покажет гонку. Это твоя первая живая data race.

**Типичные ошибки:**
- Забыли блокировать в `get`/`size` ("это же только чтение") — чтение параллельно с записью тоже гонка.
- Возвращают из `get` ссылку на значение внутри `unordered_map`: после выхода из `get` мьютекс отпущен, и другой поток может изменить/удалить элемент. Возвращай копию (`std::optional<std::string>`).
- В `handle_command` падают на пустой строке или неполной команде.

**Вопросы на понимание:**
- Зачем `mutex` помечен `mutable`? (Подсказка: тема const correctness, `get()` и `size()` — `const`.)
- Почему `get` возвращает копию, а не ссылку?
- Какая сложность у `set`/`get`/`del` в `unordered_map` и когда она может деградировать?

## Шаг 5. Подключаем ThreadPool

**Цель:** обслуживать нескольких клиентов одновременно.

Возьми `ThreadPool` из конспекта по многопоточности (`concurrency-conspect.md`) и разбери его ещё раз по строкам, прежде чем использовать — в проекте ты должен понимать его целиком.

**Скелет:**

```cpp
void handle_client(SocketHandle client, KVStore& store) {
    LineReader reader(client.get());
    std::string line;
    while (reader.read_line(line)) {
        std::string reply = handle_command(store, line) + "\n";
        if (!send_all(client.get(), reply)) break;
    }
}   // деструктор SocketHandle закроет fd

int main() {
    signal(SIGPIPE, SIG_IGN);
    KVStore store;
    ThreadPool pool(4);
    auto listener = create_listener(8080);
    while (true) {
        int fd = ::accept(listener.get(), nullptr, nullptr);
        if (fd < 0) continue;
        // TODO: положить в пул задачу "обслужить этого клиента" (см. ловушку ниже)
    }
}
```

**Ловушка, на которой споткнутся почти все:** `ThreadPool` хранит задачи в `std::function<void()>`, а ей нужен **копируемый** вызываемый объект. Лямбда, в которую ты положил `SocketHandle` (он move-only), копируемой не будет — получишь длинную ошибку компиляции. Варианты:
- Передать в лямбду **сырой `int fd`** и создать `SocketHandle` уже внутри: `[fd, &store] { handle_client(SocketHandle(fd), store); }`. Самый простой путь.
- Или положить `SocketHandle` в `std::shared_ptr`.

А теперь подумай, что будет с `fd`, если `pool.enqueue(...)` бросит исключение (или пул уже останавливается): между `accept` и созданием `SocketHandle` внутри лямбды дескриптор ничем не защищён. Как это закрыть?

**Как проверить:**
- Открой три `nc` одновременно, в каждом работай с хранилищем. `SET x 1` в одном → `GET x` в другом должен вернуть `1`.
- Нагрузка: `for i in $(seq 1 50); do (echo "SET k$i v$i" | nc localhost 8080) & done; wait`, затем проверь пару ключей через `GET`.
- Прогони это же в сборке с `-fsanitize=thread` — предупреждений быть не должно.
- Поставь пул из 2 потоков, открой три `nc` и поработай во всех трёх.

**Вопросы на понимание:**
- Почему при пуле из 2 потоков третий клиент "висит" и когда он оживёт?
- Какие данные разделяют потоки-воркеры, и чем каждое из них защищено?
- Что произойдёт, если клиент отключится посреди `send_all`?

## Шаг 6. Аккуратное завершение и таймауты

**Цель:** сервер корректно останавливается по Ctrl+C и не держит воркеров на мёртвых клиентах.

**Скелет:**

```cpp
std::atomic<bool> g_stop{false};
void on_sigint(int) { g_stop = true; }

// в main, до цикла accept:
//   struct sigaction sa{};
//   sa.sa_handler = on_sigint;          // без SA_RESTART: accept() вернёт -1 с errno == EINTR
//   sigaction(SIGINT, &sa, nullptr);
//
// цикл: while (!g_stop) { accept ...; если fd < 0 и errno == EINTR — проверить g_stop }
```

**Таймаут на неактивного клиента** (после `accept`, до передачи fd в пул):

```cpp
timeval tv{};
tv.tv_sec = 5;                                       // 5 секунд тишины — закрываем соединение
setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));
// recv вернёт -1 с errno == EAGAIN/EWOULDBLOCK, когда время вышло
```

**Головоломка для понимания:** запусти сервер, подключи `nc` и ничего не печатай. Нажми Ctrl+C на сервере. Что произойдёт, если таймаут **не** выставлен? (Подсказка: деструктор `ThreadPool` делает `join` воркеров, а воркер сидит в `recv`.) Почему таймаут это лечит, хотя и не идеально?

**Как проверить:**
- Ctrl+C на сервере с подключённым простаивающим `nc` → сервер завершается не позже чем через время таймаута.
- Сборка с `-fsanitize=address`: после остановки нет сообщений об утечках.
- `lsof -p <pid>` во время работы и после отключения клиентов: число дескрипторов возвращается к исходному.

**Типичные ошибки:**
- Обработчик сигнала делает что-то "тяжёлое" (печатает, берёт мьютекс). В обработчике безопасно только выставить флаг.
- Не закрывается слушающий сокет / не вызывается деструктор пула, потому что `main` вышел через `exit`.

## Если застрял

1. Компилятор: смотри **первую** ошибку, остальные чаще всего её следствия. Сборка с `-Wall -Wextra` ловит много.
2. Сведи задачу к минимуму: слои независимы (RAII-обёртка, чтение строк, хранилище, пул) — тестируй каждый отдельно, как в шагах выше.
3. Логи с идентификатором потока: `std::cerr << std::this_thread::get_id() << " got: " << line << "\n";` — быстро показывает, что реально происходит.
4. Системные вызовы: `strace -f ./kv` (Linux) или `dtruss` (macOS) показывают, что программа реально делает с сокетами.
5. Соединения и порты: `lsof -i :8080`.
6. Если не помогло — присылай мне: код текущего шага, **что ожидал**, **что получилось** и точный текст ошибки или вывода. С этим набором разберусь быстро.
